# 研究主張私稿：保存、重開與換機恢復

> 這是先前私稿輪的驗收紀錄。後續核對原文與確認套用的進度，請看[最新操作結果](claim-draft-application-scenarios.md)。

2026-11-02，隔離 `0.5.0.dev`。這輪接上的是共用後端；**App 尚未有新的主張編輯介面，也還不能正式套用修訂。**

| 操作情境 | 實際演練 | 必須看到／保存的結果 |
| --- | --- | --- |
| 同一主張存兩份人工解讀 | 真正 claim producer 產出被保留的候選，選目前論文，分別保存兩份私稿，再重開 | 兩份完整文字、原分析與舊目標基準保留；正式主張和同步佇列不變 |
| 連按保存 | 兩個執行緒重送十次同一稿 | 只有一筆私稿、同一 revision，沒有十份重複內容 |
| 兩個編輯視窗競爭 | 先存新版，再從較早開啟的編輯視窗保存另一份文字 | 舊稿不能覆蓋新版；呼叫方原輸入仍在，可另存新稿 |
| 收到新的正式主張 | 保存後以真正 producer 發布新版，再讀私稿 | 顯示 stale，保留原文字與原基準，不偷偷換成新版基準 |
| 另存一則無關筆記 | 保存主張私稿後新增 note | 私稿仍能接續，不因無關修改誤判過期 |
| 關閉時保存 | 分別在保存開始前、與已進入保存後關閉審閱 | 關閉後拒絕新的工作；已開始的私存仍完成，不修改正式研究 |
| 資料庫被換成副本 | 真正 SQLite backup 後替換同路徑原生檔案 | 私稿標為 foreign，文字仍可讀；舊身分不能寫進替換的資料庫 |
| 大型合法私稿 | 保存並重開超過200、未超過220 KiB的結構化文字 | 不被誤列損壞；舊的一般文字稿限制保持原值 |
| 手改私稿的權限資料 | 改 owner、paper、current、operation、parent、source、confirmation 或 baseline，再重算指紋 | 封閉格式仍拒絕，不因指紋正確就相信錯誤身分 |
| 備份後移開原資料夾 | 完整備份 → 獨立恢復 → 實際移開原資料夾 → 讀歷史稿 → 建立可編輯副本 → 明確選新目標 → 再私存 | 原文字與來源版本保留，新目標使用新工作區身分；沒有舊路徑依賴或自動套用 |
| 只看恢復稿 | 預覽前後比較獨立恢復資料庫位元組及 schema，再進行 adoption | 查看不寫入生命週期表，不破壞後續建立可編輯副本的流程 |
| 誤用一般套用／保留入口 | 對結構化稿呼叫一般 decide，分別測 Apply 和 Keep | 拒絕，不改正式研究，也不產生錯類型的決策收據 |

**最終相關群組：93項通過，其中22項新增、71項既有。**
156.74秒測試／157.92秒整輪；相同981個程式／測試輸入、零變動、零失敗／錯誤／跳過。
它包含本輪私稿與既有文字／筆記恢復、JSON／來源拒絕、保存競爭的互動檢查；不是93個新功能。

這輪測試真的抓到兩個問題：唯讀恢復預覽會建立執行期表；關閉後仍能發起新保存。
兩者已修正並以同一候選程式重跑上述群組通過。原本對未知恢復 schema 的拒絕保留。

目前只驗證本機獨立資料夾與模擬 provider。尚未驗收來源核對後的正式套用、這條主張流程的跨裝置收斂、
新編輯介面、Mac／手機安裝版或正式雲端。舊目錄已被移開的案例只證明私稿接續，不代表來源權限可直接沿用。
